Spring Security — do Zero ao Deploy

Apostila completa do projeto com.sistemalogin.security: um sistema de login com autenticação e autorização usando Spring Security 6. Cada arquivo, cada anotação e cada decisão de design explicados linha a linha — do pom.xml ao template Thymeleaf.

Spring Boot 4.0.6 Java 21 Spring Security 6 Thymeleaf H2 (mem) Lombok BCrypt JPA / Hibernate
1

Visão Geral do Projeto

O projeto security é um sistema completo de login com cadastro de usuários, autenticação via formulário, área protegida por sessão e logout seguro. Ele é construído sobre Spring Boot 4 com Java 21 e usa o Spring Security 6 como framework de segurança.

O objetivo é demonstrar, de forma prática, como implementar autenticação e autorização numa aplicação web real — com senhas criptografadas em BCrypt, banco H2 em memória e templates Thymeleaf integrados ao Spring Security.

O que este projeto implementa?
  • Cadastro de usuário com senha criptografada em BCrypt
  • Login via formulário com verificação de credenciais no banco
  • Área protegida acessível apenas para usuários autenticados
  • Logout seguro via POST com proteção CSRF
  • Regras de acesso por rota definidas no SecurityFilterChain

Entidade Usuario

A entidade Usuario representa a tabela usuarios no banco de dados. Ela é o objeto que o Spring Security vai carregar para verificar credenciais.

package com.sistemalogin.security.model;

@Data            // Lombok: gera getters, setters, equals, hashCode, toString
@Entity          // JPA: esta classe mapeia uma tabela no banco de dados
@NoArgsConstructor // Lombok: gera construtor sem argumentos (exigido pelo JPA)
@Table(name = "usuarios")   // nome da tabela no banco
public class Usuario {

  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  @Column(nullable = false, unique = true)
  private String nome;    // campo único — serve como "username"

  @Column(nullable = false)
  private String senha;   // sempre salva como hash BCrypt

  @Column(nullable = false)
  private String role;    // ex: "ROLE_USER"
}

Por que cada campo existe?

Campo

id

Chave primária gerada automaticamente pelo banco (AUTO_INCREMENT).

Campo

nome

Identificador único do usuário. Funciona como o "username" do Spring Security.

Campo

senha

Nunca salva em texto puro — sempre como hash BCrypt antes de gravar no banco.

Campo

role

Define a permissão do usuário. Neste projeto sempre será "ROLE_USER".

Por que unique = true no nome? O Spring Security exige que o "username" identifique univocamente o usuário. Se dois usuários tivessem o mesmo nome, o findByNome() poderia retornar o registro errado e causar uma vulnerabilidade de autenticação.

UsuarioRepository

O repositório é a camada de acesso ao banco de dados. Ele estende JpaRepository, que já traz os métodos básicos (save, findById, findAll…), e adiciona um método personalizado para buscar por nome.

package com.sistemalogin.security.model;

public interface UsuarioRepository extends JpaRepository<Usuario, Long> {

  Optional<Usuario> findByNome(String nome);
  // Spring Data JPA gera o SQL automaticamente:
  // SELECT * FROM usuarios WHERE nome = ? LIMIT 1
}
Como o Spring Data JPA cria o SQL automaticamente?
  • O prefixo findBy indica uma consulta SELECT
  • O sufixo Nome indica a coluna a filtrar (atributo da entidade)
  • O retorno Optional<Usuario> garante que o código trate o caso "usuário não encontrado" sem NullPointerException
Por que Optional e não Usuario diretamente? Optional força o código que chama findByNome() a tratar explicitamente o caso em que o usuário não existe no banco — evitando bugs silenciosos. No ConfiguracaoSeguranca, usamos .orElseThrow() para lançar uma exceção adequada quando o usuário não é encontrado.

Bean 1 — UserDetailsService

Este bean responde à pergunta: "Dado um nome de usuário, quem é esse usuário no banco?" O Spring Security chama esse bean automaticamente durante o processo de login.

@Bean
public UserDetailsService userDetailsService(
        UsuarioRepository usuarioRepository) {  // injeção via parâmetro

  return username -> {   // lambda: recebe o nome digitado no formulário

    Usuario usuario = usuarioRepository
        .findByNome(username)           // busca no banco pelo campo "nome"
        .orElseThrow(() -> new UsernameNotFoundException(
            "Usuário não encontrado: " + username));

    return new User(                    // User = classe do Spring Security
        usuario.getNome(),             // username
        usuario.getSenha(),            // senha (hash BCrypt)
        Collections.singleton(
            new SimpleGrantedAuthority("ROLE_USER"))  // roles
    );
  };
}

Fluxo passo a passo do login

1

Usuário envia o formulário de login

O campo name="username" do formulário HTML é capturado pelo Spring Security.

2

Spring Security chama o UserDetailsService

Passa o valor do campo username para o lambda como parâmetro username.

3

findByNome() consulta o banco

O repositório executa SELECT * FROM usuarios WHERE nome = ?

4

Usuário não encontrado → exceção

UsernameNotFoundException é lançada e o Spring Security retorna "credenciais inválidas".

5

Usuário encontrado → objeto User criado

O Spring Security compara a senha digitada (texto) com o hash BCrypt salvo no banco.

6

Senha correta → sessão criada, redirect para /area-logada

Senha errada → redirect para /login?error.

Por que Collections.singleton()? O terceiro parâmetro do construtor User exige uma Collection de authorities. Collections.singleton() cria um conjunto imutável com exatamente um elemento — perfeito para este projeto onde todos os usuários têm apenas a role ROLE_USER.

Bean 2 — SecurityFilterChain

Este bean define as regras de autorização — quem pode acessar o quê — além de configurar o formulário de login e o comportamento do logout.

@Bean
public SecurityFilterChain chain(HttpSecurity http) throws Exception {
  return http

    // ── 1. AUTORIZAÇÃO: quem acessa o quê ──────────────────────────
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/", "/cadastro", "/css/**").permitAll()
        // "/" → página inicial, "/cadastro" → cadastro público, "/css/**" → arquivos estáticos
        .anyRequest().authenticated())
        // qualquer outra rota exige que o usuário esteja autenticado

    // ── 2. LOGIN: página e redirecionamento ────────────────────────
    .formLogin(login -> login
        .loginPage("/login")                    // URL da nossa página de login customizada
        .defaultSuccessUrl("/area-logada", true)  // para onde ir após login OK
        .permitAll())                          // a rota /login é pública

    // ── 3. LOGOUT ──────────────────────────────────────────────────
    .logout(logout -> logout
        .logoutSuccessUrl("/login?logout")   // redireciona após logout
        .permitAll())

    .build();
}

Tabela de regras de acesso

RotaAcessoMotivo
/ Público Página inicial — qualquer visitante pode ver
/cadastro Público Novo usuário precisa se cadastrar antes de logar
/css/** Público Arquivos estáticos devem ser carregados mesmo antes do login
/login Público Definido via .permitAll() no .formLogin()
/area-logada Autenticado Capturado por .anyRequest().authenticated()
Qualquer outra rota Autenticado Regra residual .anyRequest().authenticated()
O que acontece quando um usuário não autenticado acessa /area-logada? O Spring Security intercepta a requisição, salva a URL original e redireciona automaticamente para /login. Após o login bem-sucedido, ele redireciona de volta para a URL original ou para o defaultSuccessUrl.

Bean 3 — BCryptPasswordEncoder

Este bean registra o algoritmo de hash de senhas. Ao declará-lo como @Bean, ele fica disponível para injeção em qualquer lugar da aplicação — inclusive no controller.

@Bean
public BCryptPasswordEncoder passwordEncoder() {
  return new BCryptPasswordEncoder();
  // strength padrão = 10 (2^10 = 1024 iterações de hash)
  // Para mais segurança: new BCryptPasswordEncoder(12)
}

Como o BCrypt funciona?

Ao cadastrar

  • Senha digitada: "minhasenha"
  • Encoder gera um salt aleatório
  • Aplica 1024 iterações de hash
  • Resultado: $2a$10$AbcXyz... (60 chars)
  • Esse hash é salvo no banco

Ao logar

  • Senha digitada: "minhasenha"
  • Spring Security chama matches(raw, hash)
  • Extrai o salt do hash salvo
  • Recalcula e compara
  • Resultado: true ou false
Nunca salve senhas em texto puro! Se o banco de dados for comprometido, senhas em texto puro expõem todos os usuários imediatamente. Com BCrypt, o atacante precisaria de um ataque de força bruta para cada senha individualmente — o que leva anos com strength 10+.

UsuarioController

O controller mapeia as 6 rotas da aplicação e processa os formulários de cadastro e de área logada.

@Controller
public class UsuarioController {

  @Autowired private UsuarioRepository usuarioRepository;
  @Autowired private BCryptPasswordEncoder passwordEncoder;

  // (A) Página inicial — pública ─────────────────────────────────
  @GetMapping("/")
  public String index() { return "index"; }

  // (B) Exibe formulário de cadastro ─────────────────────────────
  @GetMapping("/cadastro")
  public String cadastroUsuario(Model model) {
    model.addAttribute("usuario", new Usuario());
    return "cadastro";
  }

  // (C) Processa o formulário de cadastro ────────────────────────
  @PostMapping("/cadastro")
  public String cadastrarUsuario(@ModelAttribute Usuario usuario) {
    usuario.setSenha(passwordEncoder.encode(usuario.getSenha()));  // hash BCrypt
    usuario.setRole("ROLE_USER");   // define role antes de salvar
    usuarioRepository.save(usuario);
    return "redirect:/login";      // PRG: Post-Redirect-Get
  }

  // (D) Área protegida ───────────────────────────────────────────
  @GetMapping("/area-logada")
  public String areaLogada(Model model,
          @AuthenticationPrincipal User user) {
    model.addAttribute("usuarioLogado", user.getUsername());
    return "area-logada";
  }

  // (E) Exibe página de login ────────────────────────────────────
  @GetMapping("/login")
  public String login() { return "login"; }
}

Análise detalhada de cada rota

Rota C — POST /cadastro

Cadastro com hash de senha

O formulário de cadastro envia nome e senha em texto puro via POST. O controller nunca salva a senha em texto puro: antes de chamar save(), ele chama passwordEncoder.encode() para gerar o hash BCrypt. Depois define a role como "ROLE_USER" e salva.

O return "redirect:/login" implementa o padrão PRG (Post-Redirect-Get): evita que o usuário reenvie o formulário ao apertar F5.

Rota D — GET /area-logada

@AuthenticationPrincipal

A anotação @AuthenticationPrincipal User user injeta diretamente o objeto do usuário autenticado na sessão atual — sem precisar chamar SecurityContextHolder.getContext().getAuthentication() manualmente.

user.getUsername() retorna o nome do usuário e é passado ao template Thymeleaf via model.addAttribute("usuarioLogado", ...), onde é renderizado com th:text="${usuarioLogado}".

@ModelAttribute vs @RequestParam @ModelAttribute Usuario usuario instrui o Spring a mapear todos os campos do formulário HTML para os atributos do objeto Usuario automaticamente. É equivalente a fazer new Usuario() e preencher cada campo individualmente com os dados da requisição POST.

application.properties

Pontos de Atenção

Erros comuns e soluções

Erro frequente 1

Login falha sempre — "Bad credentials"

Causa mais comum: o campo do formulário não se chama username ou o UserDetailsService busca por um campo diferente do que foi digitado.

Solução: confirme que o input do form tem name="username" e que o findByNome() no repositório está buscando pelo campo correto da entidade.

Erro frequente 2

H2 Console em branco / bloqueado

Causa: Spring Security bloqueia frames por padrão (proteção X-Frame-Options) e a rota /h2-console/** não está na lista de permitidas.

Solução: adicionar .requestMatchers("/h2-console/**").permitAll() e desabilitar frame options no SecurityFilterChain.

Erro frequente 3

Senha duplicada — senha já vem criptografada do form

Causa: o encoder é chamado duas vezes (no controller e em algum outro lugar).

Solução: criptografar a senha apenas dentro do método cadastrarUsuario(), antes de usuarioRepository.save().

Erro frequente 4

403 Forbidden ao fazer logout

Causa: o logout está sendo feito via GET em vez de POST. O Spring Security rejeita logout via GET por proteção CSRF.

Solução: o botão de logout deve estar dentro de um <form method="post" th:action="@{/logout}">.

Dica de debug: habilite os logs do Spring Security Adicione ao application.properties:
logging.level.org.springframework.security=DEBUG
Isso mostra no console exatamente qual filtro está rejeitando a requisição e por quê.
