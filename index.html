Configurando o pom.xml
As dependências e o que cada uma faz no projeto

Assim que você adiciona spring-boot-starter-security ao projeto, o Spring automaticamente bloqueia todas as rotas. Seu trabalho é configurá-lo para liberar o que for necessário.

⚠️
Sem nenhuma configuração, o Spring Security gera uma senha aleatória no console e protege todas as rotas com um formulário de login padrão. Você sempre precisa customizá-lo.
XML pom.xml 
<!-- Spring Boot 3 exige Java 17 como mínimo -->
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.4.5</version>
</parent>

<dependencies>

  <!-- 1. JPA: faz a ponte entre Java e o banco de dados -->
  <dependency>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
  </dependency>

  <!-- 2. SECURITY: o coração desta aula -->
  <dependency>
    <artifactId>spring-boot-starter-security</artifactId>
  </dependency>

  <!-- 3. THYMELEAF: motor de templates HTML -->
  <dependency>
    <artifactId>spring-boot-starter-thymeleaf</artifactId>
  </dependency>

  <!-- 4. THYMELEAF + SECURITY: habilita tags sec: no HTML -->
  <dependency>
    <artifactId>thymeleaf-extras-springsecurity6</artifactId>
  </dependency>

  <!-- 5. MySQL: driver do banco de dados -->
  <dependency>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
  </dependency>

  <!-- 6. LOMBOK: elimina getters/setters/construtores -->
  <dependency>
    <artifactId>lombok</artifactId>
    <optional>true</optional>
  </dependency>

</dependencies>

Entendendo a Arquitetura
Como o Spring Security intercepta as requisições

O Spring Security funciona como uma cadeia de filtros (Filter Chain) que intercepta cada requisição HTTP antes de ela chegar ao seu Controller. Pense nele como um porteiro que verifica o crachá (autenticação) e decide quais andares você pode acessar (autorização).

1
Criando a Entidade Usuario
O modelo que será persistido no banco de dados

Este é o modelo mapeado para a tabela no banco. O Spring Security precisa de pelo menos: username, password e roles — você define como esses campos se chamam na sua entidade.

💡
Por que o prefixo ROLE_? O Spring Security espera que roles comecem com ROLE_. Ao usar .hasRole("USER") na config, o Spring adiciona ROLE_ automaticamente. Com .hasAuthority("ROLE_USER") você precisa escrever o nome completo.
Java model/Usuario.java 
@Data            // Lombok: gera getters, setters, equals, hashCode
@NoArgsConstructor// Lombok: construtor sem args (obrigatório para JPA)
@Entity
@Table(name = "usuarios")
public class Usuario {

  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  @Column(nullable = false, unique = true)
  private String email;

  @Column(nullable = false)
  private String senha;  // sempre armazenar o hash BCrypt

  @Column(nullable = false)
  private String role;   // ex: "ROLE_USER" ou "ROLE_ADMIN"
}
2
Criando o Repository
A interface que consulta o banco de dados

O Repository é a interface que faz as consultas. Você só precisa de um método customizado: buscar o usuário pelo email. O Spring Data JPA cria a query automaticamente pelo nome do método.

Java repository/UsuarioRepository.java 
@Repository
public interface UsuarioRepository
    extends JpaRepository<Usuario, Long> {

  // Spring Data cria automaticamente:
  // SELECT * FROM usuarios WHERE email = ?
  Optional<Usuario> findByEmail(String email);
}
💡
Por que Optional? Evita NullPointerException. Se o usuário não existir, retorna Optional.empty() em vez de null, permitindo usar .orElseThrow() com segurança.
3
Implementando UserDetailsService
A peça central da integração — a ponte entre banco e Security

Esta é a peça mais importante. Você está dizendo ao framework: "quando precisar autenticar alguém, use este método para buscar o usuário." O Spring Security não sabe como seu banco está estruturado — você ensina ele aqui.

Java service/UsuarioDetailsService.java 
@Service
public class UsuarioDetailsService
    implements UserDetailsService {

  @Autowired
  private UsuarioRepository usuarioRepository;

  // O Security chama este método com o campo "username" do formulário
  @Override
  public UserDetails loadUserByUsername(String email)
      throws UsernameNotFoundException {

    // 1. Busca no banco pelo email
    Usuario usuario = usuarioRepository
        .findByEmail(email)
        .orElseThrow(() -> new UsernameNotFoundException(
            "Usuário não encontrado: " + email
        ));

    // 2. Converte a role para o formato do Spring Security
    SimpleGrantedAuthority authority =
        new SimpleGrantedAuthority(usuario.getRole());

    // 3. Retorna UserDetails — objeto padrão do Spring Security
    return new User(
        usuario.getEmail(),       // username
        usuario.getSenha(),       // senha já em BCrypt
        Collections.singletonList(authority)
    );
  }
}
4
Configurando o SecurityConfig
Os 3 beans essenciais que governam toda a segurança

Esta é a classe mais importante. No Spring Boot 3, a forma correta usa @Bean com lambdas — não mais herdar WebSecurityConfigurerAdapter (que foi removido).

ℹ️
Spring Boot 3 vs 2: A API mudou do estilo antigo (herdar WebSecurityConfigurerAdapter e sobrescrever configure()) para o estilo moderno com beans e lambdas. O projeto já usa a forma correta e atual.
Java config/SecurityConfig.java 
@Configuration
@EnableWebSecurity
public class SecurityConfig {

  @Autowired
  private UsuarioDetailsService usuarioDetailsService;

  // ── BEAN 1: PasswordEncoder ──────────────────────────────
  // Nunca salve senhas em texto puro!
  // BCrypt gera um hash diferente a cada chamada, mesmo para a mesma senha
  @Bean
  public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
  }

  // ── BEAN 2: Authentication Provider ─────────────────────
  // Liga o UserDetailsService ao PasswordEncoder
  @Bean
  public DaoAuthenticationProvider authenticationProvider() {
    DaoAuthenticationProvider provider =
        new DaoAuthenticationProvider();
    provider.setUserDetailsService(usuarioDetailsService);
    provider.setPasswordEncoder(passwordEncoder());
    return provider;
  }

  // ── BEAN 3: Security Filter Chain ───────────────────────
  // Define as regras de acesso por rota
  @Bean
  public SecurityFilterChain securityFilterChain(HttpSecurity http)
      throws Exception {

    http
      // 1. REGRAS DE AUTORIZAÇÃO POR ROTA
      .authorizeHttpRequests(auth -> auth
        .requestMatchers("/cadastro", "/login", "/css/**")
            .permitAll()      // rotas públicas
        .requestMatchers("/admin/**")
            .hasRole("ADMIN")  // só ROLE_ADMIN
        .anyRequest().authenticated()  // resto exige login
      )

      // 2. FORMULÁRIO DE LOGIN
      .formLogin(form -> form
        .loginPage("/login")
        .loginProcessingUrl("/login")
        .defaultSuccessUrl("/home", true)
        .failureUrl("/login?error=true")
        .permitAll()
      )

      // 3. LOGOUT
      .logout(logout -> logout
        .logoutUrl("/logout")
        .logoutSuccessUrl("/login?logout=true")
        .invalidateHttpSession(true)    // invalida a sessão
        .deleteCookies("JSESSIONID")     // remove cookie
        .permitAll()
      );

    return http.build();
  }
}
5
Criando o Controller
Rotas de cadastro e páginas protegidas
🚨
Regra de ouro: NUNCA salve a senha em texto puro. Sempre use passwordEncoder.encode(senha) antes de persistir no banco. Salvar senha em texto puro é uma falha grave de segurança.
Java controller/UsuarioController.java 
@Controller
public class UsuarioController {

  @Autowired private UsuarioRepository usuarioRepository;
  @Autowired private PasswordEncoder passwordEncoder;

  // GET /login → exibe a página de login
  @GetMapping("/login")
  public String login() {
    return "login";  // → templates/login.html
  }

  // GET /cadastro → formulário de cadastro
  @GetMapping("/cadastro")
  public String cadastro() {
    return "cadastro";
  }

  // POST /cadastro → processa e salva o usuário
  @PostMapping("/cadastro")
  public String salvarUsuario(
      @RequestParam String email,
      @RequestParam String senha,
      Model model) {

    if (usuarioRepository.findByEmail(email).isPresent()) {
      model.addAttribute("erro", "E-mail já cadastrado!");
      return "cadastro";
    }

    Usuario novo = new Usuario();
    novo.setEmail(email);
    novo.setSenha(passwordEncoder.encode(senha));  // ← SEMPRE encodar!
    novo.setRole("ROLE_USER");
    usuarioRepository.save(novo);

    return "redirect:/login?cadastro=true";
  }

  // GET /home → página protegida (só para logados)
  @GetMapping("/home")
  public String home() {
    return "home";
  }
}
6
Views com Thymeleaf
login.html, cadastro.html e home.html
⚠️
Os campos do formulário de login devem se chamar name="username" e name="password" — esse é o padrão esperado pelo Spring Security. Se usar nomes diferentes, o login nunca vai funcionar.
HTML templates/login.html 
<html xmlns:th="http://www.thymeleaf.org"
      xmlns:sec="http://www.thymeleaf.org/extras/spring-security">

<!-- Mensagem de erro de autenticação -->
<div th:if="${param.error}">E-mail ou senha inválidos!</div>
<div th:if="${param.logout}">Você saiu com sucesso.</div>

<!--
  O Spring Security intercepta este POST automaticamente.
  Você NÃO precisa criar um método no Controller para /login POST.
-->
<form th:action="@{/login}" method="post">

  <!-- "username" e "password" são nomes padrão do Spring Security -->
  <input type="email" name="username" required/>
  <input type="password" name="password" required/>
  <button type="submit">Entrar</button>
</form>
HTML templates/home.html 
<html xmlns:th="http://www.thymeleaf.org"
      xmlns:sec="http://www.thymeleaf.org/extras/spring-security">

<!-- Exibe o email do usuário logado -->
<span sec:authentication="name"></span>

<!-- Visível apenas para ADMIN -->
<div sec:authorize="hasRole('ADMIN')">
  <p>Painel de Administração</p>
</div>

<!-- Logout: deve ser POST para funcionar com CSRF -->
<form th:action="@{/logout}" method="post">
  <button type="submit">Sair</button>
</form>
💡
Por que o logout é POST? O Spring Security exige POST para o logout por proteção CSRF. Um link GET poderia ser explorado para deslogar alguém sem consentimento.

Fluxo Completo de Autenticação
O que acontece entre o clique em "Entrar" e a tela home
1
Usuário submete o formulário POST /login com username e password — interceptado pelo Spring Security antes de qualquer Controller.
2
UsernamePasswordAuthenticationFilter Extrai as credenciais do request e cria um token de autenticação para processar.
3
DaoAuthenticationProvider Chama loadUserByUsername(email) no seu UsuarioDetailsService, que busca o usuário no banco via UsuarioRepository.
4
Verificação de senha BCrypt O BCryptPasswordEncoder compara a senha digitada com o hash armazenado no banco de dados.
5
SecurityContext atualizado Usuário fica "logado" na sessão HTTP. SecurityContextHolder.setAuthentication(...) é chamado internamente.
6
Redirect para /home Configurado em defaultSuccessUrl("/home", true) no SecurityConfig.

Erros Comuns
Os 5 problemas mais frequentes e como resolver
❌
There is no PasswordEncoder mapped for the id "null"
Você salvou a senha sem encodar, ou esqueceu de configurar o bean PasswordEncoder no SecurityConfig.
Garanta que existe o bean BCryptPasswordEncoder e que usa passwordEncoder.encode(senha) ao salvar o usuário.
❌
403 Forbidden em recursos estáticos (CSS/JS)
O Spring Security está bloqueando os arquivos estáticos da aplicação.
Adicione .requestMatchers("/css/**", "/js/**").permitAll() na configuração do SecurityFilterChain.
❌
Login sempre retorna erro mesmo com credenciais corretas
Causas mais comuns: (1) campo do form não se chama username/password, (2) senha no banco não está em BCrypt, (3) loadUserByUsername busca pelo campo errado.
Verifique os nomes dos campos no HTML, a senha no banco (deve começar com $2a$) e o campo usado no findBy.
❌
Logout via link GET não funciona
O Spring Security exige POST para logout por padrão, como proteção CSRF.
Use um <form method="post"> com th:action="@{/logout}" — nunca um link <a href="/logout">.
❌
WebSecurityConfigurerAdapter — cannot find symbol
Você está usando um tutorial escrito para Spring Boot 2.x. Essa classe foi removida no Spring Boot 3.
Use o estilo moderno com SecurityFilterChain como @Bean, conforme mostrado nesta aula.
